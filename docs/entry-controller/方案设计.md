## 技术方案概述

把当前散落在 `deploy/installer/install.sh` 中的 Caddy、external 证书与入口条件分支收敛为一个深的
`EntryController` Module。安装器只提交版本化 `EntrySpec` 并调用 `plan / reconcile / status /
remove`；Module 隐藏能力协商、证书准备、入口配置、资源所有权、两阶段切换、崩溃恢复、续订同步与
Adapter 差异。

Implementation 内部保留两个 seam：`CertificateProvider` 负责证书生命周期与 `CertificateRef`，
`IngressProvider` 负责宿主监听与请求处理。三个入口 Adapter 是两者的组合：

| Entry Adapter | CertificateProvider | IngressProvider | 用途 |
| --- | --- | --- | --- |
| `caddy-legacy` | Caddy ACME 存储 | Caddy 容器 | schema 1 默认值，保持当前安装行为 |
| `nginx-certbot` | certbot webroot | 宿主 nginx | 无外部管理系统的 standalone 部署 |
| `external` | external driver | external driver | VPS Factory nginx + certd 或其它宿主管理器 |

默认仍为 `caddy-legacy`。旧配置缺少 `entry_provider` 时，`tls_mode: external` 归一化为 `external`，
其余情况归一化为 `caddy-legacy`；本轮不改变既有安装默认值。

## Interface 选择

比较了三种方案：

1. `Reconcile / Remove` 两动作：最深，但无法直接满足安装前预览和现场状态查询。
2. `Plan / Apply / Remove`：事务表达明确，却要求调用者保存并正确使用 plan，泄漏状态机顺序。
3. `plan / reconcile / status / remove`：运维面完整，切换细节仍由 Module 隐藏。

采用方案 3。`probe` 是 Adapter 内部动作，不属于调用者 Interface；`reconcile` 自己重新观测，不能
盲信旧 plan。

```text
entryctl plan      --spec <0600-file>
entryctl reconcile --spec <0600-file>
entryctl status    --deployment <id>
entryctl remove    --spec <0600-file> [--purge]
```

所有成功输出都是 `ObservedState` 或含 `ObservedState` 的版本化 JSON。错误输出至少包含
`code / phase / resource / retryable / rollback_status / message`。稳定错误码：
`invalid_spec`、`unsupported_capability`、`ownership_conflict`、`dependency_missing`、
`prepare_failed`、`activation_failed`、`verification_failed`、`rollback_failed`、`driver_failed`。

## 能力模型

`EntryController` 根据 purpose 与拓扑计算 required capabilities，再与 Adapter 的 probe 结果做集合差；
缺能力时在 `plan` 阶段拒绝，不允许开始所有权切换。

| capability | 语义 | Web | Node direct |
| --- | --- | --- | --- |
| `certificate.material` | 能发布有效 `CertificateRef` | 必需 | 必需 |
| `certificate.issue` | 能首次取得证书 | Caddy/nginx 必需 | Caddy/nginx 必需 |
| `certificate.renew` | 能长期续订 | Caddy/nginx 必需 | Caddy/nginx 必需 |
| `certificate.notify` | 证书代次变化可触发 reconcile | 建议 | 必需 |
| `ingress.acme_http01` | 拥有 HTTP-01 webroot | Caddy/nginx 必需 | Caddy/nginx 必需 |
| `ingress.web_https` | 终止 Web TLS 并代理 UI | 必需 | 不需要 |
| `ingress.plain_fallback` | 提供内核回落的明文 HTTP | 不需要 | 有回落时必需 |
| `lifecycle.prepare` | 可在不抢活动入口端口时准备候选 | 自动切换必需 | 自动切换必需 |
| `lifecycle.rollback` | 激活失败后能恢复原入口 | 自动切换必需 | 自动切换必需 |
| `ownership.adopt` | 可接管另一 Adapter 留下的资源 | 迁移可选 | 迁移可选 |
| `stream.tcp_passthrough` | TCP L4 转发 | 后续单 443 | 后续单 443 |
| `stream.udp_passthrough` | UDP L4 转发 | 不需要 | 后续 Hysteria2 复用 |
| `stream.sni_routing` | TLS ClientHello 分流 | 后续单 443 | 后续单 443 |

M4 基线不要求任何 `stream.*` 能力。Node 的 Xray、NaiveProxy、Hysteria2 默认直接监听协议端口并
自行终止 TLS；`routes.json` 是观测、端口/防火墙校验和明文回落输入，不是 nginx 动态 L4 配置源。

## EntrySpec schema

### combined v2 扩展（Issue #22）

v1 的单域名 schema、部署 ID、external driver protocol v1 和既有 journal 均不改写。`schema_version: 2`
专用于 `topology: combined`，权威声明见 [`entry-spec-v2.schema.json`](schema/entry-spec-v2.schema.json)
和 [`combined-caddy-v2.json`](examples/combined-caddy-v2.json)。同一 `deployment_id` 固定
`domains.web` 与 `domains.node` 两个不同的小写 FQDN；首次 reconcile 必须同时声明 `web`、`node`
两个角色。`active_roles`、`roles` 与 `certificate_targets` 的键必须一致。Web 声明回环
`web_upstream`；Node 声明 `direct`、`route_manifest` 和证书消费者路径。按角色分开的
`certificate_targets` 包含受管目录、稳定 cert/key 路径与单一续订 owner。v2 目前只允许
`caddy-legacy` 目标；external v2 由 #24 协商后交付，旧 external driver 不收到 v2 spec。

卸载一个角色通过同一 deployment ID 的较高 revision、相同域名锚点及只含剩余角色的目标提交给
`reconcile`；最后一角色退出时才调用 `remove`。一旦已提交状态少了一个角色，普通 combined spec
不能把它带回来。恢复必须传 `restore_intent.roles` 和当时已提交目标的
`expected_committed_digest`。目标 SHA-256 对规范化 JSON 计算，排除 revision 和一次性的
restore_intent，并排序 active_roles。同 revision 不同目标、低 revision、变更域名锚点和 v1
journal 接管均在 Adapter 副作用前拒绝。

v2 `ObservedState` 见 [`observed-state-v2.schema.json`](schema/observed-state-v2.schema.json)。
它原子写入 0600 journal，记录已提交目标快照与 digest、候选目标、前一与候选资源身份、阶段、
active roles、域名锚点、各角色证书的路径/指纹/代次/有效期/续订 owner/消费者 hook 结果，
以及共享 80/443 和 Node 直连监听。资源记录 deployment ID、owner、role/shared scope、
保留策略及现场 marker/digest。Adapter 的只读 probe 必须重新核对现场身份；Controller 拒绝
与已提交资源身份不符的观测，首次部署遇到现有资源也拒绝自动接管。状态中只保留可证明归属的
资源；按名字或旧环境变量不能推定所有权。

控制器的 `plan/reconcile/status/remove` Interface 保持不变。v2 事务依次写入
`preparing → prepared → activating → verifying → stable`，每次副作用前先写候选目标和资源
身份。失败写 `rolling_back`，由 Adapter 根据 journal 的 **committed_target** 恢复；失败
则持久记录 `failed`。崩溃后先恢复上一份已提交目标，再尝试新目标。完全相同的已提交目标返回
`unchanged`，不调用 Adapter。`remove` 只能匹配最后一个已提交的单角色目标并再次核对资源身份。
当前生产进程未注册 v2 宿主 Adapter，因此 v2 `plan` 标明不可执行，`reconcile/remove` 返回
`unsupported_capability`；#23 将把 Caddy 宿主动作接到这些内部 Adapter 生命周期函数。

权威 schema 位于 [`entry-spec.schema.json`](schema/entry-spec.schema.json)。核心字段：

```json
{
  "schema_version": 1,
  "revision": 7,
  "deployment_id": "trojanpanelnext-node",
  "provider": "external",
  "purpose": "node",
  "domain": "node.example.com",
  "certificate": {
    "managed_dir": "/tpdata/trojan-panel-core/cert",
    "source_dir": "/etc/vps-factory/certs/node.example.com"
  },
  "ingress": {
    "node_exposure": "direct",
    "route_manifest": "/tpdata/trojan-panel-core/external/routes.json",
    "fallbacks": [{"listen": "127.0.0.1:8443", "root": "/tpdata/web"}]
  },
  "external_driver": {"protocol_version": 1, "path": "/usr/local/libexec/trojanpanelnext-entry-provider"}
}
```

不变量：`revision` 对同一 deployment 单调递增；`purpose: web` 必须给出回环 `web_upstream`；
`purpose: node` 的 `node_exposure` 在本版本只能为 `direct`；私钥和口令不进入 spec；external driver
必须是 root 所有且不可被 group/world 写，spec 通过 0600 文件传递。

## ObservedState 与所有权

权威 schema 位于 [`observed-state.schema.json`](schema/observed-state.schema.json)。状态原子写入
`${TP_DATA}/trojanpanelnext-entry/state/<deployment_id>.json`，目录 0700、文件 0600。它是恢复日志，
不能只当展示缓存。

状态至少记录：desired/observed revision、活动与前一 Adapter、phase、能力、证书指纹与代次、监听、
资源清单、续订状态、最近错误和 rollback 结果。资源项包含：

- `owner: controller`：Controller 可直接修改/删除；
- `owner: provider`：只能由当前 Adapter 操作；
- `owner: external`：Controller 只观测，必须委托 external driver；
- `retention: managed|preserve`：普通 remove 是否删除。

禁止按固定文件名或容器名推断所有权。`remove` 只操作状态清单内属于该 deployment 的资源；证书
默认 `preserve`，只有显式 `--purge`、provider 确认没有其它 consumer 后才能删除。

## 两阶段切换与崩溃恢复

phase：`stable → preparing → prepared → deactivating → activating → verifying → stable`；失败进入
`rolling_back`，无法回滚进入 `failed`。每次有副作用前先原子写 phase 与 rollback journal。

1. Normalize spec，重新 observe，拒绝旧 revision。
2. Probe 目标 Adapter，校验能力、依赖、权限、证书与端口所有权。
3. Prepare 证书和候选配置；此阶段不得抢旧入口的监听。
4. 写入旧状态快照和回滚动作，再 deactivate 旧 Adapter，但保留数据。
5. Activate 目标 Adapter，做结构化健康检查。
6. Web 验证 TLS/HTTP upstream；Node 验证证书消费者、direct 端口与必需回落。
7. 成功后提交 active provider 和 observed revision；旧数据留到后续显式 purge。
8. 失败先停目标，再按 journal 恢复旧 Adapter；两边结果都写入状态。

进程重启读到非终态 phase 时不得从头执行：`preparing/prepared` 可安全放弃候选；旧入口已停后的
phase 必须优先回滚。external driver 缺少 `lifecycle.rollback` 时只允许生成 manual handoff plan，
不能宣称自动切换。

### ACME 所有权切换

- Caddy → nginx/external：优先用仍有效的 Caddy 证书作为目标入口的启动证书，目标取得 80 后再由
  新 CertificateProvider 建立自己的续订状态，避免重复申请和无证书窗口。
- nginx/external → Caddy：Caddy 先以现有证书准备候选配置；取得 80/443 后再切换到 automatic HTTPS。
- 同一宿主 nginx 在 standalone 与 VPS Factory 间切换时优先执行资源 adoption，只切换 owner 和
  timer 单写者，不启动第二个 nginx。
- 无法取得可迁移证书且 HTTP-01 又被旧入口占用时，plan 必须返回明确停机窗口和回滚步骤。

## 证书续订 hook

续订不增加新的外部动作：Provider 的 timer/deploy hook 调用同一份持久化 spec 执行
`entryctl reconcile`。Controller 重新 probe 证书指纹；未变化返回 unchanged，变化后：

1. 原子同步 `CertificateRef`；
2. Web Adapter 执行配置校验后 reload；
3. Node 更新托管副本并重启证书消费者；第一版允许重启整个 Core；
4. Core 启动时对齐已有 Xray/NaiveProxy/Hysteria2 配置中的证书路径并刷新 `routes.json`；
5. 每一步写入 renewal generation、时间、结果与错误，证书已续订但 reload 失败不得伪装成续订失败。

一台机器只能有一个证书定时器单写者。Caddy、standalone timer 与 certd timer 切换必须进入 plan 和
ownership journal；`reload_command` 字符串不是续订闭环。

## Web 与 Node 行为

| 维度 | Web | Node |
| --- | --- | --- |
| TLS 终止 | Caddy/nginx/external ingress | Xray/NaiveProxy/Hysteria2 内核 |
| 公网入口 | 80/443 | 内核声明的独立 TCP/UDP 端口；80 保留给 ACME |
| 内部目标 | `127.0.0.1:<ui_port>` | 无统一 upstream |
| 回落 | 不需要 | 仅 `external_fallback_listener_required` 的路由需要明文 HTTP |
| routes.json | 不存在 | 观测与校验输入 |
| 443 冲突 | ingress 拥有 | 同机 Web 已占 443 时内核不得再选 443 |

Hysteria2 的协议端口是 UDP；其 traffic stats 管理端口当前并非回环监听，必须由防火墙阻断。
gRPC 只允许主控来源，MariaDB/Redis 只允许所需节点来源，UI/API 只允许本机入口。真实防火墙与
TCP/UDP 拨测属于实机验收，不能用本地 fake 结论替代。

## 三个 Adapter

### caddy-legacy

封装现有 `write_*_caddyfile / start_caddy / wait_for_cert / caddy_cert_files` 与容器生命周期。
保持 schema 1 默认、容器名、端口和证书路径兼容。第一阶段不强行改变 Caddy 存储布局；状态明确
记录 Node 证书续订后的 consumer reload 能力，不能虚报闭环。

### nginx-certbot

使用宿主 nginx + certbot webroot。只写 namespaced 配置，所有替换先生成候选、`nginx -t`、原子
替换、reload，失败保留旧配置。Node 不生成动态 stream 规则；只生成 ACME 与必要的回环明文回落。
使用独立锁和唯一 timer，导出稳定 `CertificateRef`，默认保留 lineage。

### external

通过 well-known executable driver 交互。Controller 不直接删除 nginx、certd 或外部证书目录。
driver 接收同一 EntrySpec 0600 文件，输出兼容 ObservedState schema 的 JSON；退出码区分无能力、
所有权冲突、暂时失败和不可回滚失败。若只有契约文件而没有 driver，应明确称为 contract-only，
不具备自动 reconcile 能力。

协议 v1 的逐动作状态、退出码、完整输入输出与恢复约束见
[`external-driver-v1.md`](external-driver-v1.md)。当前实现把 driver 的绝对路径和 SHA-256 写入
ObservedState；非终态恢复时两者必须完全相同，避免替换后的可执行文件继承未完成的回滚责任。

- acme↔external、`--force`、证书目录布局和权限测试。

### 迁移

- Caddyfile、启动、等待证书和 Caddy 容器操作迁入 `caddy-legacy` Adapter；
- external 证书与契约逻辑迁入 `external` Adapter 和共享证书 helper；
- `recreate_container_if_env_changed` 的 provider 迁移判断迁入 EntryController；
- 入口说明由自由文本 README 升级为 ObservedState，README 只做人类视图。

### 删除或收窄

- 删除“external 必须代理每个动态内核端口”的要求和默认 nginx stream 示例；
- `routes.json` 不再触发 M4 的全量 L4 转发；`stream.*` 只保留为未来可选能力；
- Node 配置中的 `bind_address` 文案需删除，它目前只影响 Web UI；
- 不再用散落的 `if TLS_MODE == external` 作为新 provider 扩展机制。

### 需要重做

- 当前 external 只有条件分支和 README，不是可 probe/reconcile 的 driver；
- Caddy 删除虽然应 fail closed，但还没有 journal 与自动回滚；
- 证书续订仍需人工重跑 installer/重启内核；
- 端口 warning 不能替代防火墙策略与 ObservedState；
- `"<cert>|<key>"` 字符串证书对需改为结构化 `CertificateRef`；
- `--force` 的镜像拉取行为变化与 external 无关，应单独决策，不能混入本 Module。

## 关键设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 外部 Interface | `plan/reconcile/status/remove` | 保留只读运维面而不泄漏迁移步骤 |
| 内部 seam | CertificateProvider + IngressProvider | 生命周期不同，支持安全迁移中间态 |
| schema 1 默认 | caddy-legacy | 现有用户零行为变化 |
| Node 默认拓扑 | direct | 与当前内核监听和 TLS 模型一致 |
| 入口状态 | 持久化 journal | 支持崩溃恢复和所有权安全删除 |
| 续订通知 | 同一 reconcile | 避免一次性 reload 字符串与第二套状态机 |
| nginx-certbot 实机接通 | 暂缓 | 本地 fake 不能证明端口、ACME 与 reload 正确 |

## 2026-09-14 本地稳定化增补

- `external` 已接通本地 `reconcile/remove`，严格校验 protocol v1 输出，并持久化每个副作用前的
  phase；fake driver 已覆盖旧 revision、崩溃恢复、回滚失败重试、驱动替换拒绝和 remove 幂等。
- `status` 是 journal 读取，不伪装成实时 provider 探测；实时 probe/verify 只发生在持有可信 spec
  和 driver identity 的 plan/reconcile 中。
- `nginx-certbot` 已具备确定性的候选配置、argv 描述、计划校验与临时目录 fake-system 回滚测试；
  计划固定标记 `executable:false`，尚未接通 nginx/certbot/systemd/端口/CA 的任何真实副作用。
- 通用 plan 将“能力集合满足”与“宿主 mutation 已开放”分开报告；当前只有通过 probe 的 external
  driver 会得到 `mutation_enabled/executable:true`，Caddy 与 nginx 的本地计划不会误导调用者。
- 安装器里现存的 Caddy/external 条件分支继续按迁移清单逐步收口。schema 1 缺少新 provider 字段时
  仍归一化为 `caddy-legacy`，因此本轮不改变既有安装默认行为。
