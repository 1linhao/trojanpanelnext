## 技术方案概述

安装器采用“单一命令入口 + YAML 配置文件 + 用途模式”的方式。用户通过
`install.sh` 执行安装、卸载或配置校验，通过 `--mode web|node` 明确当前主机用途，
所有部署参数均从配置文件读取，整个过程不询问问题，适合 SSH、云初始化和自动化平台。

## 技术选型

| 类别 | 选择 | 理由 |
| --- | --- | --- |
| 命令入口 | Bash `install.sh` | 延续现有部署环境，无需新增运行时 |
| 配置格式 | YAML | 保留已有配置生态，复杂值比 shell source 文件安全 |
| 配置读取 | `yq` | 现有引擎已使用，避免通过 `eval` 或 `source` 执行配置内容 |
| 部署实现 | 收敛到唯一的 `install.sh` | 只维护一套容器、证书和数据卷部署逻辑 |

## 架构设计

`install.sh` 是唯一入口，负责 CLI、参数校验和部署执行；内部模块负责配置读取、用途一致性检查、
环境准备和容器生命周期。配置使用 `trojanpanelnext` 根节点，并以 `purpose` 声明用途。

## 模块划分

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| CLI 入口 | 解析 `install/remove/validate`、`--mode`、`--config` | 部署引擎 |
| 配置层 | 读取 `trojanpanelnext` 配置根、校验用途和必填项 | `yq` |
| Web 主控部署 | API、Web、MariaDB、Redis、Caddy | Docker |
| Node Agent 部署 | Agent、mTLS 公开 CA、证书与本地生成的伪装站 | Docker、Web 主控数据库与 Redis |

## 接口设计

```text
install.sh install  --mode web  --config web.yaml
install.sh install  --mode node --config node-agent.yaml
install.sh validate --mode web  --config web.yaml
install.sh remove   --mode node --config node-agent.yaml
```

配置契约：

```yaml
trojanpanelnext:
  schema_version: 1
  purpose: web
```

CLI 的 `--mode` 与配置中的 `purpose` 必须一致，避免将 Node 配置误用于主控服务器。

## 关键设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 是否交互 | 完全非交互 | 可重复执行并适合自动化 |
| 用途来源 | CLI 与配置双重声明 | 防止误部署 |
| 历史兼容 | 不保留 | 新项目只维护一套明确、可测试的接口 |
| 控制通道 | 仅 mTLS | Web 自动生成客户端身份，Node 只分发公开 CA |
| 密钥输出 | 不在终端打印 | 降低日志泄露风险 |
| 镜像来源 | TrojanPanel Next GHCR `latest` 或显式版本 | 与新仓库发布工作流一致 |

## 发布稳定性与维护性优化计划

本节纳入当前“裸机独立部署、版本化安装资产、候选 tag 发布”的交付目标。优化分为候选版前的稳定性门禁和候选版验收后的结构优化，避免以大范围重构阻塞已经可验证的发布路径。

### 候选版前必须完成

1. **发布清单单一来源**：由 `deploy/installer/release/generate-assets.sh` 生成版本化资产与 manifest；CI 重新生成 example manifest，并以 `git diff --exit-code` 拒绝手工 SHA 漂移。`install.sh` 的摘要必须以版本替换后的生成资产为准，而不是工作区源码文件。
2. **安装器副作用顺序**：依赖预检完成且允许主机变更后，才写入 EntryController runtime 资产、systemd timer 和其他宿主资源；`TP_INSTALL_DEPS=0` 的失败路径不得调用安装、写入或删除类主机命令。
3. **续期 hook 环境契约**：renewal hook 必须在干净环境中携带已验证的 EntryController 路径、Caddy root、镜像 digest、timer backend 和状态根；缺少可用 timer backend 时 fail-closed，并把 journal 标记为 degraded。
4. **发布级回归门禁**：候选 tag 前必须通过 `release_assets_test.sh`、`installer_cli_test.sh`、入口契约测试、真实隔离 Caddy Docker smoke，以及 hook 脱离父 shell 的续期测试；timer owner marker 被删除、篡改或归属其他 deployment 时必须拒绝继续操作。

### 候选版验收后、正式版前

1. **Caddy Adapter 深模块化**：将续期 trigger 生命周期、consumer registry、timer ownership 和 certificate purge 从 `caddy.sh` 拆为职责单一的 provider-neutral 模块；外部接口保持 `probe/prepare/activate/verify/rollback/remove` 不变。
2. **清单与代码防漂移**：把 manifest 生成、版本替换、摘要校验封装成一个 CI helper，避免安装脚本、示例清单和测试各自维护哈希规则；失败时上传生成 manifest 与差异作为 CI artifact。
3. **CI 反馈加速**：缓存 Go module、前端依赖和已验证的 Docker 镜像；保持 API、Web、Node、installer 和真实 smoke 并行，仅在相关路径变化时跳过无关工作。
4. **故障证据标准化**：所有真实 smoke 失败保留状态 journal、hook stderr、容器日志和生成 manifest；本地复现命令与 CI 命令保持一致，减少“本地绿、CI 红”的环境差异。

### 本地快速验证路径

完整 GitHub CI 仍是合并与发布门禁，但日常修改先走本地快速路径，避免每次等待远程 runner：

```bash
# 安装器或 EntryController 改动（约数秒）
find deploy/installer -type f -name '*.sh' -print0 |
  while IFS= read -r -d '' f; do bash -n "$f"; done
bash deploy/installer/tests/installer_cli_test.sh
bash deploy/installer/tests/entry_controller_test.sh
```

combined/Entry 改动再追加 `bash deploy/installer/tests/entry_combined_v2_test.sh`、`bash deploy/installer/tests/entry_caddy_adapter_test.sh` 和 `bash deploy/installer/tests/combined_install_test.sh`；这些测试不依赖远程 runner，通常比一次 GitHub CI 往返快一个数量级。再按变更范围追加定向检查：API/Node 改动运行对应目录的 `go test ./...`，Web 改动运行对应的 UI 测试，文档或发布资产改动运行文档构建和 manifest 重新生成并检查 `git diff --exit-code`。只有跨模块改动、合并前或候选 tag 才运行完整 CI、Docker smoke、全历史 secret scan 和真实 VPS 验收。

该分层不降低发布门禁：本地快速路径用于缩短反馈周期，GitHub CI 仍负责干净环境、完整历史和并行矩阵验证；任何本地与 CI 不一致都保留 CI 结果并补充最小复现证据。

### 当前目标纳入关系

- 候选版发布的阻塞项是上面的四项稳定性门禁；完成后才允许创建 `v0.1.0-rc.1` tag。
- Caddy Adapter 模块拆分、CI 缓存和故障 artifact 纳入同一项目目标，但排在候选 VPS 验收之后、正式版 tag 之前。
- 真实 VPS、DNS、ACME 和云安全组仍属于人工门禁；本计划不扩大自动化权限边界。

## 技术方案概述

一份统一 YAML 驱动同一套 `init → check → deploy` 命令。配置以稳定宿主标识描述一台 Web 主控所在宿主和可追加的 Node Agent 列表；同一宿主标识表示同机部署，不按 IP、SSH 地址或服务域名推断。该方案等待 GitHub 规格 #34 的新增拓扑与依赖图重新获批后实施。

## 技术选型

| 类别 | 选择 | 理由 |
| --- | --- | --- |
| 操作入口 | 既有 Bash CLI、OpenSSH、mikefarah yq v4 | 延续已约定的操作机依赖与安装资产 |
| 安装执行 | 既有 `web`、`node`、`combined` 安装器模式 | 用户只有一种编排流程，内部沿用已定义的部署模式与资源所有权 |
| 身份同步 | Web 主控公开 Node 身份 CLI/API | 由控制面登记并验证数据库身份，不直接写 SQL 或复制 Web 私钥 |

## 架构设计与模块划分

统一配置包含宿主集合、Web 所引用的宿主、`nodes[]` 中每个 Node 的稳定键和宿主引用。每个宿主显式声明 `local` 或 `ssh`；仅 Web 宿主可为 `local`，因此操作机可以是外部电脑或 Web VPS，不能是独立 Node VPS。相同宿主标识只允许 Web 与最多一个本机 Node；该 Node 可以使用与 Web 不同的服务域名。其他 Node 各使用独立的 SSH VPS。服务地址与 SSH 连接地址分开声明。

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| 配置与拓扑规划 | 校验宿主引用、Node 稳定键、同机数量与部署路径 | 统一 YAML、yq v4 |
| 只读预检 | 按唯一宿主汇总依赖、DNS、端口、资源与所有权；`local` 不走 SSH | 拓扑规划、现有安装器状态接口 |
| 发布与安装 | 一次计划/确认；分机时 Web/Node 安装，同机时使用单次 `combined` 安装 | 已校验 Release、固定镜像 digest、既有安装器 |
| Node 身份编排 | 为新增 Node 在 Web 登记、生成加密引导包、安装并验证；旧 Node 只核对/收敛 | Web 官方身份 CLI/API、Node 引导包 |

## 接口与数据模型

配置中的宿主标识是机器身份，Node 稳定键是控制面身份，Web/Node 服务域名是网络地址，三者不能互相代替。一个 Node 的稳定键重跑时必须对应同一 Web 登记身份；名称、域名、版本或凭据发生不允许的变化时停止并告知冲突。新增 Node 先核对 Web 数据库中是否已有该身份，再按既有登记流程写入并验证；不能只在 YAML 中新增条目就宣称同步成功。删除 YAML 条目不自动卸载或撤销现有 Node。

## 关键设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 同机判断 | Web 与 Node 使用相同宿主标识 | 避免 NAT、域名或地址复用导致误部署 |
| 同机部署 | 复用现有 `combined` 模式，首版最多一个本机 Node | 共享入口与容器所有权不能安全地由两次独立安装拼成 |
| 追加 Node | 同一 `deploy` 增量执行，先核对旧身份，只登记新身份 | 支持安全续跑，避免重复注册或静默轮换 |
| 操作机 | 仅外部电脑或 Web VPS；Web 本机宿主使用 `local` | 不把含 Web 高权限密码的统一配置放在独立 Node VPS |

## 实现计划与验证

GitHub 规格 #34 为权威验收契约；先修订 #35–#40，并拆出 Web 多 Node 身份契约与 combined 编排工单，完成依赖图审批后逐票独立 worktree/PR 实现。测试覆盖外部电脑分机、Web VPS 本机分机、Web+一个本机 Node，以及在上述基础上追加独立 Node；验证只读 `check`、确认前零副作用、Web 数据库登记、幂等续跑、不同域名、失败后旧 Node 不受影响、HTTPS 与 Web→Node mTLS/gRPC。真实 VPS、DNS、ACME、安全组和清理仍须单独人工批准。

## 技术方案概述

新部署在每台宿主只使用 `/tpdata/trojanpanelnext` 作为 TrojanPanel Next 业务数据根；原容器内 `/tpdata/...` 位置不作为宿主路径直接复用。目标 VPS 上的底层安装器 `remove` 自动移除归属可证明的本项目容器与无人引用的受管镜像，普通卸载保留根目录；只有最后一个角色退出并显式 `--purge-data` 时才彻底清除该根。操作机统一 CLI 本轮仍只含 `init/check/deploy`，不新增跨 VPS 卸载。此方案及拟议 ADR-0005 等待 GitHub 规格和依赖图的人工批准。

## 技术选型与架构设计

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| 宿主路径映射 | 把 Web/Node/combined 的数据库、配置、凭据、证书、日志、Entry 状态和保留发布资产归入固定根；逐项映射到容器内既有路径 | 现有安装器与 Node 引导包配置 |
| 资源归属记录 | 持久记录 deployment ID、随机所有权标记、受管容器及发布镜像 digest；检查挂载和引用 | 发布清单、Docker inspect、EntryController 状态 |
| 底层卸载 | 在变更前核验归属，按身份/入口/容器依赖顺序移除，最后只清理无人引用的受管镜像 | 资源归属记录、现有 remove Interface |
| 显式彻底清除 | 确认无剩余角色后校验根目录的规范路径、属主、标记和符号链接，再删除专属业务根 | 底层卸载、受管根 |

## 接口与数据模型

沿用目标 VPS 上的 `install.sh remove --mode web|node|combined --config ...`；`--purge-data` 表示“最后角色卸载并彻底清除业务数据”。combined 只移除一个角色时传此选项应在副作用前拒绝，而不是悄悄删除共享根或假装已彻底清除。普通 `remove` 自动清理受管容器和在全 Docker 容器集合中无人引用、且发布清单与归属记录均能证明的镜像 digest；不使用全局 prune、宽泛 tag 删除或强制删除被外部容器占用的镜像。删除失败逐资源报告并保留可续跑状态。

## 关键设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 数据布局 | 固定宿主根，逐项映射原容器内路径 | 一条路径可清业务数据，又不让 Node 容器看到 Web 或数据库私钥 |
| 部署冲突 | 继续停止并点名旧/外来资源 | 自动清理只在明确的 `remove` 命令触发 |
| 旧版数据 | 不迁移、不自动删除 `/tpdata` 下的旧分散布局 | 用户自行清理；避免把旧资源误判为新部署所有物 |
| 根外资源 | systemd 单元、运行脚本和外部证书依其所有权契约单独清理 | `/etc`、`/usr/local` 和外部证书目录不得被根目录递归删除覆盖 |

## 独立 Node 撤销与本机卸载衔接（#46，拟议 ADR-0006）

用户已确认正常流程先在 Web VPS 撤销，再在 Node VPS 卸载；Node 突然失联或销毁时，Web 强制撤销必须独立成功。现有官方 `revoke` 和 `force-evict` 已提供控制面生命周期，拟补充成功回执以衔接本机卸载，具体安全契约如下。

1. Web 持有专用撤销签名密钥，私钥仅存在 Web 受管数据根并以 0600 保存。只把公钥加入受校验且加密的 Node 引导包，在 Node 首次安装时固定信任；不复用 TLS CA 私钥，不自动替换已安装 Node 的公钥。
2. 官方 Web CLI 完成 MariaDB/Redis 权限回收、身份终态与审计记录后，才允许原子导出回执。强制撤销还移除活动节点登记；Node 不可达不是失败条件。Web 侧部分失败、结果不确定或密钥缺失时返回非零，不输出可用成功回执。
3. 回执使用版本化有界格式，签名覆盖固定协议标识和原始负载；负载绑定签发者公钥指纹、identity ID、server ID、撤销代次上限与 revoked/evicted 终态。核验不得从待验证回执自身接受新的信任公钥。
4. 独立 Node 的底层 remove 接收回执文件，先用已安装公钥验证签名和身份绑定，再核对本机代次不高于撤销代次上限；全程不需要连接 Web。此前代次已经失效的旧 Node 也能用该身份的终态回执卸载。普通部署或另一身份不能重用该回执。
5. 回执可供同一已撤销身份重复卸载和失败续跑，不设计成消费后丢失的一次性令牌。容器/数据归属、剩余角色、外部引用与显式 purge 条件仍分别核验。combined 仍复用同宿主官方撤销调用和既有顺序。
6. 原 VPS 已销毁时，只执行 Web `force-evict` 即完成授权回收；不要求在不存在的 Node 上验证回执或删除资源。旧版缺少预置信任公钥的部署不自动接管或迁移，按用户已确认的旧数据策略处理。

验证覆盖错误签发者/身份、篡改签名、过旧回执、本机旧代次、撤销部分失败、重复导出与重复卸载；以隔离 MariaDB/Redis 验证旧凭据失效、其他 Node 不受影响，以及断开 Node 后 Web 强制撤销仍成功。具体序列化与签名库由实现选择标准库能力，不自行实现密码学原语。
