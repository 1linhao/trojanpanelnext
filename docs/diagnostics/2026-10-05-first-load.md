## 放大因素

### 1. 静态资源没有压缩

线上 Caddyfile 站点段仅包含 `reverse_proxy 127.0.0.1:8888`。Nginx 使用默认关闭的 gzip。携带 `Accept-Encoding` 的请求仍返回完整 `Content-Length`，没有 `Content-Encoding`；浏览器记录中的 encoded/decoded 大小也一致。

四份首屏入口 JS/CSS 合计 445,880 B。对相同文件本地使用 gzip level 6，合计为 143,767 B，减少约 67.8%。这是实测体积差异，不是上线后耗时的保证。

仓库安装脚本 `scripts/deploy/install.sh` 的 `write_web_caddyfile()`（第 417 行起）生成同样没有压缩指令的配置，需要同时考虑安装模板和现有服务器配置。Caddy 的 `encode zstd gzip` 可启用相应响应压缩，参见 [Caddy 官方 encode 文档](https://caddyserver.com/docs/caddyfile/directives/encode)；Nginx gzip 默认关闭，参见 [Nginx 官方 gzip 文档](https://nginx.org/en/docs/http/ngx_http_gzip_module.html)。

### 2. Logo 比首屏入口资源总和还大

`/api/image/logo` 实际返回 460,503 B、1153×1080 的 JPEG。它在响应头中被标记为 `application/octet-stream` 和 `attachment; filename=logo.png`。单独下载实测 4.556 秒，服务器本机约 5 毫秒。

浏览器记录里的多个同 URL 条目有请求合并/缓存命中，不能把每个条目的 decoded 大小累加成实际重复下载量。

Logo 在页面上仅作小图标展示，缩小尺寸、优化编码和设置正确图片类型可以减少额外传输。因为图片本身已经压缩，开启文本 gzip 无法替代图片优化。

### 3. 首屏资源及动态加载链

HTML 的 `#app` 初始为空，页面依赖 module JS 启动 Vue。入口和两个 vendor bundle 必须加载；登录页还有后续动态模块请求。纽约链路上每个串行阶段都会叠加网络往返时间。

`apps/control-plane/web/vite.config.mjs` 第 55 行设置 `cssCodeSplit: false`，使首屏加载全局 CSS；manualChunks 将非框架依赖统一放入 vendor-dependencies。可进一步分析首屏是否需要全部样式和依赖，但当前明确且优先级最高的体积优化是压缩。

响应未设置明确的 `Cache-Control`/`Expires`，但有 Last-Modified/ETag；本次缓存访问确实命中了浏览器启发式缓存。不能说浏览器缓存被关闭。显式缓存策略主要改善后续访问，并不能消除全新浏览器首次下载。

## 已排查的其他方向

- 服务器低负载，静态文件与公开接口在本机均为毫秒级，没有观察到 CPU、内存或磁盘处理瓶颈。
- 本次首次访问的 DNS 解析约 5–134 毫秒，不足以解释 8–38 秒等待。
- 所有已观测的页面请求均来自同一站点，没有 Google Fonts、外部 CDN 等第三方请求阻塞首屏。
- `/api/auth/setting` 本机约 7 毫秒，浏览器常规约 0.25–0.30 秒；登录页 `created()` 发起配置和验证码请求，没有 await 它们来阻止表单挂载。
- 验证码接口尾斜杠触发一次 301，额外增加往返，但量级较小，不是数十秒静态下载的主因。

## 优化优先级

1. 先为静态 JS/CSS/HTML 启用压缩，在现有 Caddy 配置和安装模板保持一致；改后检查 `Content-Encoding` 和浏览器传输体积，再复测无缓存首屏。
2. 优化 Logo 的展示尺寸和编码，修正响应图片类型。先验证视觉质量再替换。
3. 给带内容 hash 的静态资源明确的长期缓存策略；HTML 使用可及时更新的策略。不要把登录/验证码/管理 API 一并缓存。
4. 如压缩后境内仍有明显波动，评估静态资源边缘缓存或更适合目标用户线路的机房；该项需要针对目标网络实测，不能仅凭区域名称保证改善。
