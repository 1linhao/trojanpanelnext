# 本机与 web 机网络传输诊断

测试日期：2026-10-05，Asia/Shanghai。原始传输试验在 19:05–19:12，真实页面拥塞控制对照在 21:19–21:26 执行。目标为 `trpl.lhsiteb.site` 和同一台 `ssh web` 服务器。本机通过 WLAN 接入，web 机位于 DigitalOcean NYC。

## 判断

已复现的主要瓶颈是本机到 web 机的广域网传输：部分 TCP 连接出现重传和确认等待，CUBIC 发送窗口降到很小，导致几万字节的页面资源也要等待数秒至数十秒。服务器本地处理、网卡队列和本机到网关的延迟，均没有显示足以解释这个量级等待的瓶颈。

这是端点观测能确定的直接机制。丢包、乱序和确认延迟都可能触发重传；本次没有双端逐包比对，因此不将重传次数直接解释为链路丢包率，也不能确定问题发生于哪一个运营商或路由器。不同连接的质量差异很大，多路径选路或逐流拥塞是待验证的解释。

## 原始连接与线上 HTTPS

| 测量 | 结果 | 含义 |
| --- | --- | --- |
| 本机到网关，连续 300 次 ping | 0% 丢失；平均 1.067 ms，最大 40.653 ms | 存在一次级别的本地抖动，无法解释十几秒的持续下载 |

| 18.54 秒的 256 KiB 下载 | 29 次重传；结束 cwnd=4；重传字节 41,760 B | 下载慢与小发送窗口、重传同时出现 |

| web 网卡与 fq_codel 队列 | 网卡错误/丢弃为 0，队列 dropped=0、backlog=0 | 未观察到服务器出口队列丢弃 |
| web 机本地访问 Nginx | 首页/入口 JS/Logo/公开配置中位数约 1.13/1.03/3.87/2.93 ms | 服务器本地响应与外网等待相差几个数量级 |

TCP MTR 的目的端 10 次探测全部返回，RTT 233.6–1269 ms。中间节点的高“不回应”比例可能是探测限速，不能据此确定真实业务流量在某一跳丢包。目的端探测全部返回也不能否认已测到的 TCP 数据重传。

固定 256 KiB 的原始传输试验中，系统自带 BBR 的四次单连接下载为 3.91、1.34、4.97、4.10 秒；CUBIC 的另外四次为 1.22、1.18、1.18、13.50 秒（18.54 秒为额外冒烟测试）。好线路下 CUBIC 也很快，不能仅凭一对样本说 BBR 总是更快。两个方向的上传样本为 1.35 和 1.21 秒，上传没有复现同等程度的慢速，但样本不足以推断长期上下行差异。

四条 TCP 连接各下载 64 KiB 时，合计 256 KiB 的墙钟时间为 CUBIC 2.96 秒、BBR 1.98 秒。同一轮中有的连接无重传，有的连接发生重传。这只能说明多连接有时可以分散慢连接影响；增加连接同时增加握手成本，不能由此直接要求浏览器关闭 HTTP/2 或拆成多个域名。

## 真实页面 CUBIC / BBR 对照

在 web 机建立两个临时 HTTPS 入口，代理同一 Nginx、同一前端和 API，使用同一证书、HTTP/2 和 gzip。通过监听 socket 的 `TCP_CONGESTION` 选项设置算法，生产 Caddy 的 443 端口和系统默认算法全程保持 CUBIC。临时入口只处理本次测试客户端的连接。

每次启动独立 Chromium 进程和全新上下文，不复用浏览器资源缓存、Cookie、连接或 TLS 会话。完整就绪要求登录输入框可见、公开配置加载成功、验证码与 Logo 解码完成。试验顺序为 CUBIC、BBR、BBR、CUBIC、CUBIC、BBR、BBR、CUBIC；之后交换两组端口，重复同一顺序。

两组临时入口的静态资源传输均为 175,931 B。生产 Caddy 使用 zstd，前次实测为 156,633 B，因此临时入口的结果适合组间比较，不应当作生产 443 的最新加载时间。交换端口可以减少固定端口造成的偏差，仍不能消除随时间变化的线路因素。

| 阶段 | 算法 | 尝试次数 | 完成次数 | 完整就绪中位数（秒） | 成功样本范围（秒） |
| --- | --- | ---: | ---: | ---: | ---: |
| 第一次端口分配 | CUBIC | 4 | 4 | 16.817 | 11.987–37.340 |
| 第一次端口分配 | BBR | 4 | 4 | 7.891 | 4.696–14.917 |
| 交换端口后 | CUBIC | 4 | 3 | 37.885 | 12.553–41.304 |
| 交换端口后 | BBR | 4 | 4 | 7.912 | 5.182–10.956 |
| 合计 | CUBIC | 8 | 7 | 26.683 | 11.987–41.304 |
| 合计 | BBR | 8 | 8 | 7.891 | 4.696–14.917 |

CUBIC 有一次测量在 49.627 秒时仍未显示输入框，触发脚本的输入框等待超时；这次没有计为成功或从统计中删除。该样本完整就绪时间的下界已大于各组中间样本，因此尽管其最终时间未知，上表中位数仍可确定。BBR 的 8 次全部完成，页面成功样本没有脚本异常或资源请求失败。

交换端口后改善仍然存在，合计中位数减少约 70%。这是当前线路、小样本下的实验结果，不代表生产 443 或所有境内访问线路已经达到该速度。最慢的 CUBIC 连接观测到 cwnd=1、79 次重传、RTO=1.92 秒；BBR 连接仍有几十次重传，但部分连接保持了较大的窗口。因此改善来自更能维持传输，并不表示 BBR 消除了线路异常。

## HTTP 协议对照

实际线上 443，下载同一份 59,950 B gzip JS，四轮交替顺序，每次使用全新 curl 进程，成功且验证实际协议版本：

| 协议 | 四次总耗时（秒） | 中位数（秒） |
| --- | --- | ---: |
| HTTP/1.1 | 3.554、1.191、1.231、1.989 | 1.610 |
| HTTP/2 | 2.239、1.168、3.732、1.235 | 1.737 |
| HTTP/3 | 1.506、0.784、0.840、2.356 | 1.173 |

HTTP/3 在这些小样本中更快，但仍有波动。当前 Caddy 已响应 `Alt-Svc: h3=":443"`，HTTP/3 实际可用；Cloudflare 公共 DNS 查询没有返回该域名的 HTTPS 类型记录。首次访问时浏览器如何发现并使用 HTTP/3，还需要按目标浏览器验证，不能把 curl 强制 HTTP/3 的时间当成浏览器首访保证。

QUIC 的独立流可以减轻 TCP 丢包对其他流的队头阻塞，但资源依赖、实际网络拥塞和丢包仍然存在。依据：[RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html)。

## 可优化的方式

1. **先灰度 BBR，再在原 443 上做真实页面复测。** 临时页面试验用于确认其是否值得上线试验，不能保证所有境内运营商都有同等收益。保留现有 fq_codel，先只改拥塞控制，避免同时调整多个变量。记录 Caddy 监听连接的实际算法，并覆盖不同时间段、不同境内运营商的首次加载和超时比例。更改 `tcp_congestion_control` 默认值只影响新连接；被动连接继承监听 socket 的算法，需要重新创建 Caddy 的监听 socket 才能验证实际生效。依据：[Linux 内核文档](https://docs.kernel.org/networking/ip-sysctl.html)、[BBR 官方 FAQ](https://github.com/google/bbr/blob/master/Documentation/bbr-faq.md)。
2. **让静态 JS/CSS 从实测更稳定的边缘节点提供。** 哈希文件名的 `/static/*` 适合长缓存；公开 Logo 需要先加入版本号或更新时的缓存失效机制。认证、验证码、用户接口不纳入静态缓存。域名目前直接解析到源站，使用了 Cloudflare DNS 并不等于正在使用 CDN。选择 CDN 或更近区域前，用当前境内线路比较边缘节点的冷/热缓存以及回源时间；不能假设任意 CDN 都更快。Cloudflare 的默认缓存按文件扩展名判断，HTML/JSON 默认不缓存，具体规则见[官方缓存文档](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)。
3. **进一步减少首屏下载体积与依赖等待。** 继续分析入口 JS 与登录模块的串行依赖，评估合理预加载、降低公开 Logo 编码体积、减少登录页必须加载的依赖。它能减少高 RTT 与慢连接的放大效应，但不能修复网络线路。
4. **保留并验证 HTTP/3。** 已经可用，无需重复“开启”；应测浏览器首次访问实际协议以及不同网络的 UDP 可用性。该项作为补充，不能替代线路与拥塞控制改善。

不优先做：增加服务器 CPU/内存、盲目修改 MTU/缓冲区、增加“JS 下载线程”、全站强制 HTTP/1.1。当前测量没有证明这些是主要瓶颈。
