# 管理员修改账号密码出现 5000ms 超时

排查日期：2026-11-04（Asia/Shanghai）。操作为管理员在账号列表编辑其他账号，接口为 `POST /api/account/updateAccountById`。

## 结论与线上证据

主要原因是 **web 到节点管理端口不通，而密码修改同步等待节点撤销旧凭据的串行重试**。前端 Axios 默认超时只有 5 秒。

- 线上 API 请求日志中，多次该接口耗时 72–77 秒。
- API 文件日志 `/tpdata/trojan-panel/logs/trojan-panel.log` 同时记录两台节点的 `RemoveAccount` 调用 `DeadlineExceeded`。
- 本次从 web 机对以下目标各做一次 TCP 连接检查，超时上限 4 秒，两者均约 4012ms 后超时：

| 节点管理地址 | 从 web 机连接结果 |
| --- | --- |
| `52.230.33.22:8100` | TCP connect timeout |
| `156.238.121.216:8100` | TCP connect timeout |

这证明检查时 web 无法完成到这些管理端口的 TCP 握手。节点未监听、防火墙/安全组、地址失效或线路丢弃，仍需节点侧证据区分；不能仅凭超时确定其中一种。

排查没有发送真实改密请求、修改账号、登录凭据或线上服务配置，没有创建临时服务器或远端测试文件。

## 等待如何形成

1. `web/src/api/account.js` 的 `updateAccountById` 没有覆盖 `web/src/utils/request.js` 的 `timeout: 5000`。
2. `api/service/account.go:UpdateAccountById` 在更新数据库之前，先查询旧连接凭据，调用 `RemoveAccount`。
3. `service.RemoveAccount` 对节点服务器逐台同步调用，不只处理当前账号正连接的某一个节点。
4. `core/api_grpc.go:RemoveAccount` 每次 RPC 上限 4 秒，共尝试 3 次。`retry.Delay(8s)` 未指定固定等待算法；当前 retry-go 默认是指数退避加少量随机抖动，两个重试等待约为 8 秒、16 秒。
5. 单台失联节点约耗时 `4×3+8+16=36 秒`；两台串行约 72 秒，与线上实际请求耗时吻合。

因此，即使浏览器到 web 的连接正常，该请求也远超前端的 5 秒上限；不能将此次超时直接归因于此前的境内首次访问网络波动。

## 伴随问题

- 节点撤销调用的错误被 `service.RemoveAccount` 忽略，之后仍可进入数据库更新。浏览器超时不会取消这里独立创建的 gRPC 上下文；**前端显示失败不能证明密码没有改变**。本次没有读取或验证目标账号的密码，无法判定哪次提交最终生效。
- 账号修改采用全局 Redis 锁，redsync 当前默认租期为 8 秒，没有为此长操作续租；72 秒远超租期。线上同一时段同时出现 `lock already taken` 与 `unlock failed`。
- 某些早返回路径没有释放锁，且表单没有覆盖整个请求生命周期的防重复提交处理。持续重试会放大锁竞争，部分锁失败请求本身就耗时约 4–5 秒，加上网络等待也容易超过 5 秒。
- HTTP 日志中的 `200` 不等于业务成功；项目的成功和失败响应都使用 HTTP 200，应结合 JSON 业务码判断。

## 修复方向

优先检查并恢复 web 到这两台节点的管理通道；若节点已废弃，应按实际部署状态处理，而非盲目删除仍在使用的节点。

代码方面应给节点撤销设置总时间预算、合理的有界并行和明确的部分失败处理，避免改密被串行退避拖到一分钟以上。撤销失败不能继续静默当成功，也不能直接跳过旧凭据撤销而忽略节点仍接受旧凭据的问题。

同时修复锁的释放和租期/续租策略，评估按账号加锁；表单增加提交中状态，避免重复请求。最后根据后端明确的处理时间预算设置改密专用超时与结果核对机制。仅把全局 Axios 超时调大，不能修复节点不通和锁失效。
