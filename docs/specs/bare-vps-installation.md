# 裸机安装与多模式部署规格

> 状态：已发布为 GitHub Issue #1。测试 seam 已由用户确认，规格使用 `ready-for-agent` 标签。

## 问题陈述

TrojanPanel Next 已有面向 `web` 和 `node` 的安装器雏形，但当前交付仍要求操作者从源码仓库取得脚本和模板，Node 安装依赖手工复制共享数据库、Redis 凭据与 CA 材料，同一宿主上的 Web 主控与 Node Agent 也没有正式的 `combined` 部署模式。全新的生产 VPS 无法仅凭一个版本化配置和项目正式发布资产，安全、可复现地完成安装。

操作者需要一种不依赖 VPS 管理系统、不依赖本地源码构建，并能在 Debian 12 x86_64 裸机上完成 Web 主控、独立 Node Agent 或 combined 部署的正式产品路径。该路径必须控制凭据暴露、明确网络责任边界，并在命令返回成功前证明服务真实可用。

## 解决方案

TrojanPanel Next 发布一套与产品镜像同版本的版本化安装资产。操作者先下载并编辑统一 YAML 配置，再运行经校验的 bootstrap；安装器根据 `web`、`node` 或 `combined` 部署模式安装依赖、拉取由 digest 固定的镜像、配置入口与身份、执行端到端健康检查并输出网络放行清单。

Web 主控通过 CLI 登记 Node 并生成使用 `age` 加密的 Node 引导包。每个 Node 使用独立且可撤销的 MariaDB、Redis ACL 和控制面身份。combined 部署在同一宿主上复用本地数据服务和一个共享入口，同时为 Web 与 Node 的两个域名管理证书。

## 用户故事

1. 作为生产环境操作者，我希望从 GitHub Release 下载与指定版本匹配的配置模板和 bootstrap，从而无需克隆源码仓库即可安装。
2. 作为生产环境操作者，我希望安装资产和容器镜像都有不可变摘要，从而能够复现并审计一次安装。
3. 作为生产环境操作者，我希望用一个 YAML 明确选择 `web`、`node` 或 `combined`，从而让服务器职责清晰可验证。
4. 作为裸 VPS 操作者，我希望安装器默认补齐 Docker、`age` 和必要工具，从而能在全新 Debian 12 x86_64 上直接开始安装。
5. 作为受控环境操作者，我希望设置 `TP_INSTALL_DEPS=0` 后安装器只做依赖预检并一次列出缺项，从而避免它修改系统软件。
6. 作为 Web 主控操作者，我希望首次安装自动生成数据库、Redis 和管理员强密码，并保存到权限受限的配置中，从而避免固定默认密码。
7. 作为 Node 管理员，我希望在 Web 主控上用 CLI 登记 Node 并生成加密引导包，从而不必手工拼装数据库、Redis 和 CA 参数。
8. 作为安全管理员，我希望每个 Node 使用独立的数据库用户、Redis ACL 用户和控制面登记，从而可以单独撤销受损节点。
9. 作为 Node 管理员，我希望轮换 Node 凭据时获得新引导包并立即使旧包失效，从而控制长期凭据泄露风险。
10. 作为故障处置人员，我希望 Node 失联时可从 Web 主控强制踢除它而不等待远端响应，从而及时回收数据层和控制面权限。
11. 作为 combined 部署操作者，我希望一个共享入口为 Web 与 Node 的两个域名处理 ACME，从而避免两个入口争抢 80/443。
12. 作为已有入口系统的操作者，我希望选择 external 入口方式，从而让既有证书和入口继续承担 TLS。
13. 作为网络管理员，我希望安装器根据双方公网 IP 输出最小网络放行清单和暴露告警，从而可以正确配置主机防火墙和云安全组。
14. 作为生产环境操作者，我希望安装器在同版本重跑时安全收敛非破坏性配置变化并拒绝破坏性变化，从而避免静默清库或重建身份。
15. 作为生产环境操作者，我希望卸载默认保留数据，只有显式请求时才清除，从而降低误操作造成的数据损失。
16. 作为生产环境操作者，我希望安装命令只有在 HTTPS、API 登录、数据库、Redis 和 Web 到 Node 的 mTLS/gRPC 全部通过后才成功，从而不把仅处于 `running` 的故障容器误报为可用。
17. 作为发布维护者，我希望在 CI 中验证安装资产、manifest、attestation 与镜像 digest 的一致性，从而阻止不完整或混合版本发布。
18. 作为项目维护者，我希望在真实 Debian 12 VPS 上验证分机和 combined 拓扑，从而有证据证明裸机安装路径可以投入生产使用。

## 实现决策

- 使用统一配置 schema，顶层部署模式只允许 `web`、`node` 或 `combined`；命令模式与配置不一致时失败。
- 首个正式支持平台为 Debian 12 x86_64。其他发行版和 ARM64 不作为本规格验收条件。
- GitHub Release 同时包含 bootstrap、配置模板、安装器、不可变发布清单、SHA256 校验材料和 GitHub artifact attestation。bootstrap 与配置必须绑定显式版本，不能默认使用 `latest`。
- 不可变发布清单记录每个产品镜像的 digest；安装执行以 digest 为准，避免 tag 被覆盖后改变安装结果。
- 默认自动安装运行所需依赖。`TP_INSTALL_DEPS=0` 时不得安装任何依赖，必须在改变容器或数据前完成预检并一次报告所有缺项及 Debian 12 安装建议。
- 默认入口方式使用 ACME。external 入口方式继续作为可选 Adapter，并遵循现有入口控制器的资源所有权约定。
- combined 部署要求 Web 与 Node 使用两个不同域名，由同一共享入口拥有 80/443 和两张证书；Node 内核协议端口仍保持内核直连。
- Web 首次安装生成高强度 `sysadmin` 初始密码以及 MariaDB、Redis 凭据，写入权限为 `0600` 的实际配置；终端只提示保存位置，不打印密码。
- Web CLI 提供 Node 登记、引导包生成、凭据轮换、撤销和强制踢除能力。登记输入至少包括 Node 名称、域名和公网 IP，并产生稳定的 Node 身份。
- Node 引导包使用 `age` scrypt 口令加密，默认从终端安全读取口令，也允许通过 `TP_NODE_BUNDLE_PASSWORD` 注入。包是长期、可重复使用的静态材料，但轮换或撤销后必须失效。
- Node 引导包不得包含 Web CA 私钥或 Web mTLS 客户端私钥；Web 到 Node 的 mTLS 保持由 Web 持客户端证书、Node 信任控制面 CA 的方向。
- 每个 Node 使用独立 MariaDB 用户与 Redis ACL 用户。权限限制到 Node 实际需要的表、命令和 key 范围，业务账户与协调数据仍然共享，不承诺每 Node 数据隔离。
- 强制踢除在 Node 不可达时仍能撤销登记、MariaDB 用户、Redis ACL 用户及控制面授权；它不承诺删除失联服务器上的进程、证书或数据。
- 分机配置明确声明 Web 和 Node 的公网 IP。安装器生成网络放行清单、检查明显暴露风险，但不修改 nftables、ufw 或云安全组。
- 同版本重跑允许安全收敛非破坏性配置变化。域名、身份、数据位置等破坏性变化必须在变更前拒绝并给出人工处理建议。
- 卸载默认保留生成数据和配置；只有显式 `--purge-data` 才删除。清理 Node 时先回收控制面身份，再处理本机容器。
- 安装成功必须依赖端到端健康检查，而非容器状态。失败时返回非零并保留足够诊断信息，不打印秘密。
- 资产真实性采用 SHA256 与 GitHub artifact attestation；文档提供 attestation 强验证方式。

## 测试决策

- 安装器 CLI 契约是最快反馈 seam：以版本化 YAML 和引导包为输入，断言 `validate`、安装、卸载的退出码、用户可见错误、同版本收敛和破坏性变更拒绝。测试外部行为，不依赖内部函数布局。
- 宿主编排 trace 是无特权 CI seam：使用 fake Docker、包管理器、网络和证书命令记录调用，验证三种部署模式、combined 共享入口、依赖安装开关、容器所有权和网络放行清单。
- Node 身份生命周期从 Web CLI 入口验证创建、轮换、撤销和强制踢除。MariaDB grants 与 Redis ACL 优先使用真实测试容器证明权限边界，不只比较生成的 SQL 或命令文本。
- 发布 seam 验证 Release manifest、资产 SHA256、attestation 元数据和镜像 digest 一致，且模板与安装器 schema 同版本。
- Docker 冒烟测试必须验证目标容器健康、HTTPS、Web API 管理员认证、部署身份访问 MariaDB/Redis，以及 Web 到 Node 的 mTLS/gRPC。
- 最终验收使用两台临时 Debian 12 x86_64 VPS 和两个已解析域名：先完成 Web/Node 分机部署，再清理并验证 combined 部署。真实 VPS、DNS、ACME、云安全组和清理操作需要人工批准。
- 现有安装器 CLI 契约测试与入口控制器测试作为行为基线保留并扩展。

## 范围之外

- 跨版本升级、数据库迁移回滚和自动 restore。
- Ubuntu、其他 systemd Linux、ARM64 和其他 CPU 架构的正式支持。
- 完全离线安装包。
- 自动修改 nftables、ufw 或云厂商安全组。
- 为每个 Node 提供业务数据完全隔离。
- 由 Node 通过公网注册 API 自注册。
- 自动删除失联 Node 宿主上的进程或数据。
- 依赖任何 VPS 管理系统、管理面板或本地源码构建。

## 补充说明

- 首版交付目标是全新生产环境安装，不应把“同版本收敛”描述为升级能力。
- `web` 应先建立 Web 主控和 Node 身份签发能力；独立 `node` 安装消费已生成的 Node 引导包。combined 可在同一安装事务中完成本地登记和身份交付。
- 安装器输出的网络放行清单是操作者配置防火墙与云安全组的依据，不代表网络隔离已经自动完成。
- 真实 VPS 验收所需服务器和测试域名由用户提供。
